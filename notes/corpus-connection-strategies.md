# 자료 연결 방식과 선택 조건

상태: 실제 질의·갱신 사례 대기 · 구현·효과 미검증 · 정리일: 2026-09-29

현재 접근으로 근거를 찾거나 갱신하기 어려운 사례와 사용할 자료가 생길 때 재개한다. 아래 수단 목록은 개발할 기능 목록이 아니며, 필요한 수단만 비교한다. 외부 자료의 확인일은 맨 아래의 2026-09-22 기록을 유지한다.

중심 질문은 다음과 같다.

**어떤 조건에서 어떤 자료 연결 수단을 조합해야 에이전트가 근거를 찾고 이해하며 변경 이후에도 지식을 유지할 수 있는가?**

아래 방식과 조합은 검토 후보이며, Mekra에서 효과가 검증된 구현 패턴이나 필수 구성은 아니다.

## 채택된 판단과 연구 범위

정본과 파생물의 책임은 [원자료와 파생물](../okf/external-sources.md), 선별과 내재화의 경계는 [대량 자료의 지식 구성](../okf/large-corpus.md)에 둔다. facet과 구현 수단이 일대일 대응하지 않는다는 판단은 [facet의 역할과 경계](../okf/facet-boundaries.md)에 반영했다.

[Large corpus](../facets/large-corpus.md)는 규모나 복잡성 때문에 선별·탐색 방식이 달라지는 환경의 진입점이다. 이 노트는 그보다 넓은 자료 연결 문제를 다룬다. 작은 자료에서도 정밀한 관계 표현, 외부 시스템 조회, 원문 배치 확인이 중요할 수 있다.

## 같은 목록에 놓였지만 역할이 다른 수단

전수 Markdown 변환, PDF 인덱스, 온톨로지, corpus DB, API, 기타 DB는 서로 배타적인 대안이 아니다. 하나의 구성 안에서도 함께 사용할 수 있다.

| 논의한 수단 | 주로 판단할 역할 | 구분할 점 |
| --- | --- | --- |
| 자료 전수 Markdown 변환 | 원문을 읽고 검색하기 쉬운 파생 표현 | 변환 범위와 지식 내재화 범위는 별개다. 표·그림·배치의 의미 보존도 확인한다. |
| PDF 등에 붙는 인덱스 | 문서·구간·페이지·표·그림으로 돌아가는 탐색 경로 | 문서 목록, 요약, 주석, 검색 색인은 서로 다른 일을 할 수 있다. |
| 온톨로지 | 개념·관계의 의미와 제약을 명시적으로 표현 | 링크가 있는 그래프나 그래프 DB를 쓴다는 사실만으로 같은 역할이 생기지는 않는다. |
| Corpus DB | 자료 집합을 보존하고 조회하는 역할 | 단일한 기술명이 아니다. 원문, 메타데이터, 추출물과 검색 색인을 함께 또는 따로 관리할 수 있다. |
| API | 자료나 질의 기능에 접근하는 경로 | 저장소·DB·검색 기능을 노출할 수 있으며, 그 기능을 대체하는 별도 저장 방식은 아니다. |
| 기타 DB | 업무 사실, 표 데이터, 관계 등 구조화된 내용의 관리·질의 | 업무 정본인지, 복제본인지, 재생성 가능한 탐색용 파생물인지 확인한다. |

이 구분은 선택을 돕기 위한 설명이며 새 메타데이터 분류 체계가 아니다. 대상에 이미 있는 도구와 자료 흐름부터 살펴본다.

## 검토할 구현 선택지

다음은 고정된 단계나 완성해야 할 목록이 아니다. 실제 질문과 자료를 바탕으로 필요한 부분만 비교한다.

| 선택지 | 검토할 상황 | 확인할 질문 |
| --- | --- | --- |
| 원문 직접 접근 | 현재 도구가 필요한 원문을 읽을 수 있을 때 | 별도 파생물을 만들지 않아도 근거 구간을 찾고 해석할 수 있는가? |
| 전수 텍스트·Markdown 파생본 | 넓은 범위를 반복해서 탐색·인용할 때 | 반복 활용의 이익이 변환·검수·갱신 비용을 상회하는가? |
| 필요 구간 추출·OCR와 캐시 | 접근 대상이 일부에 집중될 때 | 재요청 때 다시 추출할지, 교정한 결과를 보존할지 무엇으로 판단할 것인가? |
| 문서별 인덱스·주석 | PDF의 페이지·표·그림·문단을 찾아야 할 때 | 원문 개정이나 재배치 이후에도 같은 근거를 확인할 수 있는가? |
| 메타데이터 목록 | 출처·기간·주제 등으로 먼저 후보를 좁힐 때 | 선별에 필요한 정보가 실제로 있고 유지되는가? |
| 주제 지도·계층적 요약 | 여러 자료를 가로지르는 질문의 시작점을 찾을 때 | 요약이 놓친 조건과 반례를 원문에서 확인할 경로가 있는가? |
| 전문 검색 | 정확한 용어·문구를 찾을 때 | 표기 차이 때문에 놓치는 자료와 인용 구간 주변의 맥락을 어떻게 확인할 것인가? |
| 의미 검색·혼합 검색 | 질문과 원문의 표현이 다를 때 | 유사한 문장을 찾은 것과 실제 근거를 찾은 것을 어떻게 구별할 것인가? |
| 구조화된 DB 질의 | 레코드 필터링·집계·관계 조회가 중요할 때 | 질의 결과의 의미를 정의하는 기준과 원래 레코드를 추적할 수 있는가? |
| 관계 그래프·온톨로지 | 관계 탐색이나 명시적 의미·제약이 필요할 때 | 자유로운 연결로 충분한가, 관계의 정의와 제약을 별도로 관리할 실익이 있는가? |
| API·여러 출처의 통합 조회 | 자료가 외부 시스템에서 관리될 때 | 접근 권한, 조회 조건과 자료 갱신이 근거의 재확인에 어떤 영향을 주는가? |

## 온톨로지를 함께 운영한다는 가설

가설은 **반복적으로 관계를 조회하거나 엄밀한 의미·제약을 다뤄야 하는 환경에서, 온톨로지가 Mekra의 지식 운영을 보조할 수 있다**는 것이다. 소개에 기록한 지적 영향과 실제 구현의 유효성은 서로 다른 주장이다. 영향이 있었다고 해서 온톨로지 계층을 이미 사용하거나 검증했다는 뜻은 아니다.

가능한 구성을 두 가지로 나누어 검토할 수 있다.

- **기존 온톨로지가 정의의 정본인 경우:** 개념·관계의 정의는 그곳에서 관리하고, 관련 OKF 개념은 판단에 필요한 이유·조건·맥락을 내재화한다. 정의가 바뀌었을 때 어떤 설명을 고쳐야 하는지 확인한다.
- **온톨로지나 그래프를 파생물로 만드는 경우:** 기존 정본에서 탐색·질의용 표현을 만들고, 생성·교정·재생성의 책임을 정한다. 파생물을 수정할 때 정본에 반영할 변경인지도 구분한다.

이는 검증 후보인 구성이다. 온톨로지를 항상 Mekra의 고정된 하위 계층으로 두거나, 자연어 지식 전체를 온톨로지로 옮겨야 한다는 결론은 아니다. 자료 규모와 형식화의 필요는 별도로 판단한다. 작은 자료에서도 엄밀한 관계가 중요할 수 있고, 큰 자료에서도 검색과 요약만으로 목적을 달성할 수 있다.

## 조합을 검토하는 예

다음은 설명용 가상 사례이며 권장 preset이나 관찰된 성공 사례가 아니다.

- PDF 자료에서는 원문 보존, 문서 목록, 필요한 페이지만 OCR, 페이지별 근거 연결을 조합하고, 반복되는 판단 기준을 OKF에 남기는 구성을 시험할 수 있다.
- 외부 업무 DB에서는 API나 질의로 현재 레코드를 읽고, 용어·계산 조건·예외를 OKF에서 설명하는 구성을 시험할 수 있다. 모든 레코드를 Markdown으로 복제할 필요가 있는지는 별도로 판단한다.
- 관계 정의가 중요한 자료에서는 기존 온톨로지를 정본으로 유지하면서 자연어 맥락을 연결하는 구성과, 기존 문서에서 탐색용 그래프를 생성하는 구성을 비교할 수 있다.

## 다음 검증

실제 자료와 반복되는 질문을 골라, 현재 방식으로 **근거 찾기 → 주변 맥락 이해 → 판단 → 원자료 변경 후 갱신**을 수행해 본다. 어디서 막히는지 확인한 뒤 가장 작은 수단을 추가해 비교한다.

관찰할 것은 올바른 근거 구간을 찾았는지, 결론이 그 근거의 조건을 보존하는지, 변경 시 오래된 인덱스·요약·개념을 발견하고 갱신했는지, 이를 위해 탐색 시간과 유지 비용이 얼마나 들었는지다. 검색 성공이나 검사 통과만으로 의미의 정확성을 판단하지 않는다.

온톨로지 가설은 특히 단순한 링크·자연어 정의와 비교해 어떤 반복 질의나 변경에서 차이가 나는지 확인한다. 유효한 조건과 비용이 드러난 뒤 재사용 가능한 판단만 관련 개념·pattern에 반영한다. 아직 구현이나 효과 검증 결과는 없다.

## 참고한 구현 자료

외부 자료 확인일: 2026-09-22. 아래는 각 수단의 기능을 확인하기 위한 1차 자료이며, Mekra와의 조합 효과를 입증하는 자료는 아니다.

- [W3C OWL 2 Overview](https://www.w3.org/TR/owl2-overview/): 형식적 의미를 가진 온톨로지 표현의 한 예. 모든 온톨로지가 OWL을 써야 한다는 뜻은 아니다.
- [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/): 인용문과 텍스트 위치 등으로 대상 구간을 지정하는 표현의 예. 원문 변경 이후 연결의 유효성은 별도로 확인해야 한다.
- [SQLite FTS5](https://www.sqlite.org/fts5.html): 전문 검색과 원래 콘텐츠를 별도로 두는 색인 구성의 예.
- [pgvector](https://github.com/pgvector/pgvector): PostgreSQL 안의 벡터 유사도 검색 및 전문 검색과의 조합 예.
