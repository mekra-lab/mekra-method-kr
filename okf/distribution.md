# 연구와 다국어 배포의 동기화

`mekra-method-dev`는 연구와 채택한 공통 지식의 정본이고, `mekra-method-kr`과 `mekra-method`는 각각 한국어와 글로벌 영문 배포판이다. 동기화의 목적은 공개 가능한 지식의 의미를 맞추는 것이다. 연구 원자료나 내부 Git 이력을 함께 배포할 필요는 없다.

## 공개 범위와 언어별 책임

배포할 파일을 명시적으로 선별하고, 목록에 있는 파일도 변경된 내용을 다시 읽어 공개 적합성을 판단한다. [공개 경계](disclosure-boundary.md)에 따라 경로와 접근 가능성이 같더라도 새 내용까지 공개 가능한 것으로 간주하지 않는다. `notes/`와 `experiments/`의 일반적인 안내는 공개할 수 있지만 실제 사례와 원자료는 별도로 판단한다. 연구개발 전용 도구와 기록도 자동 배포 대상에 포함하지 않는다.

연구개발 저장소에서 비공개 연구 입력을 보존할 필요가 있다면 보존 권한과 필요성을 먼저 확인하고, 공개 가능한 연구 설명과 분리한 `research-private/`를 사용한다. 이 이름의 경로는 공개 목록이나 배포 전용 예외에도 넣지 않는다. `notes/`와 `experiments/`에도 공개 대상 파일이 있으므로 연구용 디렉터리라는 이유만으로 비공개라고 가정하지 않는다. 별도 경로는 파일 혼입을 막는 경계이며, 공개 문서 본문에 옮긴 내용의 공개 적합성은 여전히 검토해야 한다.

한국어판은 선별한 공통 지식을 반영하고, 영문판은 같은 의미·조건·예외·판단 근거를 전달한다. 번역 과정에서 원칙을 추가하거나 약화하지 않는다. 제목, 언어판 안내, 사용 예시의 저장소 URL과 저장소 자체의 역할 설명은 각 판에 맞게 조정한다. 공식 OKF 버전과 각 배포판의 동기화 기준은 서로 다른 정보다.

## 라이선스 범위

공개 배포판은 별도 표시가 없는 파일에 Apache-2.0을 적용한다. 복사·수정해 대상 저장소에 흡수하도록 제공하는 `templates/`는 README를 포함한 전체 파일을 [CC0-1.0](../templates/LICENSE)으로 제공한다. 템플릿을 이용하는 조건으로 Mekra Method 출처나 적용 기록을 남기도록 요구하지 않는다. 이 예외는 `templates/` 밖의 문서나 실험용 scaffold까지 확대되지 않는다.

CC0 적용과 이후 내용 추가 시에는 해당 내용에 대한 권한과 제3자 고지를 확인한다. 공개 목록에는 `templates/LICENSE`를 포함하고, 공개판 루트의 Apache-2.0 `LICENSE`는 유지한다. 공개판의 기본 라이선스를 dev 전체에 적용한 것으로 해석하지 않으며, dev 전용 `scripts/`의 라이선스 결정은 보류한다.

## 에이전트의 판단과 도구의 확인

에이전트는 마지막 반영 이후의 변경을 비교하고, 배포판에서 직접 고친 내용을 보존할지 공통 지식에 반영할지 판단한다. [맥락 파급](context-propagation.md)에 따라 관련 개념·facet·템플릿을 갱신하고 영문판의 의미를 검토한다. 도구는 명시한 파일의 존재, 링크, 내용의 변경 여부와 동기화 기록을 확인한다. 해시가 맞는다는 사실은 번역의 정확성이나 공개 적합성의 증명이 아니다.

공개 전에는 작업 폴더뿐 아니라 실제 전송할 커밋과 새로 공개될 중간 이력의 파일 경계도 확인한다. 마지막 상태에서 파일을 삭제해도 이전 커밋에 남아 있으면 함께 공개되기 때문이다. 검증한 커밋과 대상 원격 기준을 고정해 전송하며, 검증 이후 원격이 달라졌다면 다시 확인한다. 이 검사는 허용된 파일 안의 민감한 내용이나 번역의 의미를 자동 판정하지 않는다.

도구의 회귀 테스트는 다룬 사례에서 검사기가 의도대로 동작하는지 확인한다. 그 통과가 지식망 전체의 의미적 정확성까지 보장하지는 않는다. 검사에서 드러난 차이는 검토할 근거이며, 어느 판의 내용을 어떻게 바꿀지는 의미와 공개 범위를 보고 판단한다.

배포판별로 검토한 원본 기준과 결과물의 내용 지문을 기록하면 이후 원본 변경과 배포판의 직접 수정을 구분할 수 있다. 일부만 완료됐다면 그 범위를 그대로 보고하며, 두 배포판이 모두 확인되기 전에 전체 동기화가 끝났다고 기록하지 않는다. 공개 저장소는 각자의 이력을 유지하고 선별한 파일 변경만 받는다.

배포판의 Git 이력은 동기화 작업 자체보다 사용자가 보게 될 의미 변화를 설명한다. 커밋 메시지는 마지막 반영 이후 쌓인 dev 커밋과 실제 배포 diff를 함께 보고 그중 주요 변경을 해당 저장소의 언어로 자연스럽게 축약한다. `동기화`, `sync`, `배포 반영`처럼 작업 행위만 적은 제목은 사용하지 않는다. 여러 변화가 함께 배포되면 이력을 읽을 때 가장 중요한 변화가 드러나도록 대표 변경을 제목에 두고, 필요한 세부만 본문에 남긴다.

## 릴리스와 적용 기준

동기화는 배포할 내용의 의미와 원본 기준을 맞추는 일이고, 릴리스는 검토한 상태에 나중에도 비교할 수 있는 이름을 붙여 발행하는 일이다. 기본 적용 진입점은 각 공개판의 `releases/latest`이며, 실제 문서를 읽는 기준은 시작할 때 확인한 정식 릴리스의 태그가 가리키는 공개판 커밋이다. 릴리스 설명에는 해당 공개판 저장소와 전체 커밋 SHA를 적용 기준으로 명시하고, 그 커밋에 고정된 README와 적용 안내를 직접 연결한다. `SYNC.json`의 dev 커밋은 배포 원본을 추적하는 기준으로 구분한다. 본문 표기와 발행 순서는 [버전 안내](../versions/README.md#릴리스-본문의-적용-기준)에 둔다. 기준점을 남기면 [장기 피드백](feedback.md)에서 당시 가이드와 현재 가이드의 차이를 설명할 수 있다.

공개 `main`은 검토한 공개 문서의 최신 상태로 유지한다. 적용 의미를 유지하는 오류·표현·링크·사용성 개선은 검토 후 수시로 반영할 수 있다. 적용 판단이나 핵심 원칙을 바꾸는 변경은 dev 또는 준비 브랜치에서 검토하고 릴리스 발행과 함께 공개 `main`에 반영한다. 변경 범위는 파일명이나 수정량이 아니라 의미로 판단하며, 공개 `main`을 미발행 원칙의 staging 공간으로 사용하지 않는다. README에는 기본 적용 기준과 현재 문서가 다를 수 있음을 안내한다.

수시 반영한 개선을 정식 적용 기준에도 제공하려면 새 릴리스를 발행한다. 긴급 수정이 정식 적용 기준에 필요할 때도 변경 영향에 맞는 릴리스로 발행한다. 의미를 유지하는 수정에는 패치 릴리스를 쓰고, 적용 의미가 달라지면 그에 맞는 변경 수준을 판단한다. 배포판의 `SYNC.json`은 해당 공개 상태를 검토한 dev 기준과 공개 목록, 원본·결과물의 내용 지문을 보존한다. 공개 내용을 갱신하면 검토 기록도 갱신하고, 기존 릴리스의 기록은 태그 안에 보존한다. dev에 후속 변경이 쌓였다는 이유만으로 공개판의 기록을 다시 쓰지 않는다.

한국어판과 영문판의 같은 릴리스 이름은 같은 dev 기준에서 검토한 공통 지식을 뜻한다. 각 판의 Git 이력과 커밋은 유지하고, 동기화 기록으로 원본과 결과물의 관계를 연결한다. 한쪽만 발행됐다면 공통 릴리스가 완료된 것으로 보고하지 않는다. 발행한 태그의 대상을 옮기면 이전 사용자가 참조한 의미가 달라지므로 수정은 후속 변경으로 남긴다.

릴리스는 참고하기 쉬운 배포 기준이며, 릴리스와 다른 공개 `main`이나 릴리스 후보·dev의 가이드를 사용한 대상까지 정확히 식별하지는 못한다. 대상이 실제 읽은 공개판의 저장소와 커밋, 적용 범위를 함께 확인하면 당시 선택을 더 정확하게 해석할 수 있다. 이름과 기준 기록 방식은 [버전 안내](../versions/README.md)에 둔다. Mekra의 주·부·패치 버전은 방법론이 기존 적용에 주는 변화의 수준을 나타내며, 공식 OKF 명세 기준은 릴리스 설명에 별도로 기록한다. 적용 기준을 적었다는 사실이 대상 지식의 최신성이나 전체 전환 완료를 보증하지는 않는다.

## 배포판에서 돌아오는 변경

[피드백](feedback.md)이나 직접 수정에서 공통 지식의 개선이 발견되면 dev의 관련 개념에 반영한 뒤 필요한 배포판으로 돌려보낸다. 언어별 표현 문제는 해당 판에서 해결할 수 있다. 배포판의 수정 내용을 비교하지 않고 덮어쓰거나, 같은 지식을 서로 독립적으로 관리하는 [정본](source-of-truth.md)으로 갈라놓지 않는다.

2026-09-20의 적용 안내 링크 보완은 이 흐름의 실제 사례다.[^application-link-fix] 영문판에만 있던 내재화 개념 링크가 판 사이의 파일 목적지 대응 검사에서 드러났고, 문맥에 유용한 연결로 판단해 dev와 한국어판에도 반영했다. 이 사례는 차이를 검토해 공통 지식으로 되돌린 과정을 보여주며, 다른 도메인에서의 효과까지 입증하지는 않는다.

[^application-link-fix]: [한국어판 적용 안내의 변경 커밋](https://github.com/mekra-lab/mekra-method-kr/commit/5ee3ca639f4fd85a4370d3826e6df4d71c43b0ca). 링크를 보완한 실제 변경의 근거다.
