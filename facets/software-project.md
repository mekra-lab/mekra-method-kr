# Software project

소프트웨어 코드와 설정이 구현 사실의 주요 정본인 환경을 보는 facet입니다. 코드만으로는 충분히 드러나지 않는 지식을 무엇으로 볼지 판단하는 데 도움을 줍니다.

## 이 관점에서 중요한 점

- 코드와 설정이 이미 충분히 표현하는 구현 세부사항을 OKF에 다시 소유하지 않습니다.
- 목적, 경계, 업무 규칙, 설계 의도처럼 구현만으로 오해 없이 알기 어려운 의미는 OKF에 내재화할 가치가 있습니다.
- README, ADR, 운영 문서 등 기존 문서가 맡고 있는 정본과 작업 안내의 역할을 확인합니다. 별도 관리할 실익이 있는 안내는 `docs/` 등 기존 문서 위치를 활용하고, 관련 개념의 이해와 판단에 필요한 맥락은 정본의 변경 책임을 명확히 하면서 OKF에 내재화합니다.
- 코드나 설정의 변경이 개념의 의미·조건·판단 기준을 바꾸면 관련 OKF에도 그 영향을 반영합니다.
- 파일·디렉터리 배치는 기존 저장소 관례와 실제 작업 방식에 맞게 판단합니다.

## 판단 질문

- 코드·설정·기존 문서가 이 내용을 정본으로 이미 충분히 표현하고 있는가? 관련 개념을 이해하고 판단하려면 OKF에 어떤 맥락이 더 필요한가?
- 구현 사실이 아니라 목적·제약·업무 의미·설계 판단을 설명해야 하는가?
- 이번 구현 변경으로 의미가 달라지는 OKF 개념이 있는가?
- `ready`, 성공, `dry-run` 같은 이름이 실제로 보장하는 결과와 실행 범위는 무엇인가? 기본 동작의 예외나 호출자별 차이도 [개념의 의미](../okf/knowledge-internalization.md#상태와-결과의-의미)에 반영되어 있는가?
- 지식은 개발 에이전트가 참조하는가, 제품 AI의 입력으로도 연결되어 있는가? [실제 사용을 확인한 범위](../okf/adoption.md#지식-구성과-실제-사용의-연결)는 어디까지인가?
- 브랜치·worktree 통합 뒤에도 인용한 내용과 버전에 맞는 [근거 경로](../okf/source-of-truth.md#현재-정본과-과거-근거의-경로)를 찾을 수 있는가?
- 새 디렉터리나 문서를 만들기보다 기존 위치와 관례를 활용하는 편이 더 자연스러운가?
