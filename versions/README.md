# Versions

upstream OKF의 변화를 추적하고 이 저장소의 원칙·pattern·facet에 미치는 영향을 기록합니다. 그 명세를 해석·적용하는 Mekra Method의 릴리스 기준도 함께 다룹니다.

- [`current.md`](current.md): 현재 권장 기준과 확인한 upstream 기준점
- [`migrations/`](migrations/): 버전 간 실제 전환이 필요한 변경

## 명세와 가이드의 기준

| 기준 | 의미 |
| --- | --- |
| OKF 명세 버전과 확인한 파일 기준점 | 어떤 공식 형식을 해석·적용하는가 |
| Mekra Method 릴리스 태그 | 채택한 방법론과 운영 지식의 고정된 배포 기준점 |
| 참고한 배포판의 저장소와 커밋 | 대상에 적용할 때 실제로 읽은 가이드의 상태 |

기본 적용 기준은 각 공개판의 최신 정식 릴리스이며, `releases/latest`를 공식 적용 진입점으로 사용합니다. 공개 `main`은 검토한 문서의 최신 상태로, 적용 의미를 유지하는 오류·표현·링크·사용성 개선은 릴리스 사이에도 반영할 수 있습니다. 적용 판단이나 핵심 원칙이 바뀌는 변경은 dev 또는 준비 브랜치에서 검토한 뒤 릴리스 발행과 함께 공개 `main`에 반영합니다. 변경 범위는 파일명이나 수정량이 아니라 의미로 판단하며, 미발행 원칙을 공개 `main`에서 시험하지 않습니다. 대상 번들의 `okf_version`에는 공식 명세 버전을 사용하고 Mekra Method 릴리스 이름을 넣지 않습니다.

공개 `main`의 개선을 정식 적용 기준에 포함하려면 새 릴리스를 발행합니다. 긴급 수정이 정식 적용 기준에 필요할 때도 같은 절차를 따릅니다. 의미를 바꾸지 않는 오류·표현·링크 수정은 패치 릴리스로, 적용 의미가 달라지는 수정은 아래 변경 수준에 맞는 릴리스로 처리합니다. 긴급성만으로 패치 버전을 선택하거나 기존 태그를 옮기지 않습니다.

`SYNC.json`은 해당 공개 상태가 어느 dev 커밋과 공개 목록을 기준으로 검토됐는지, 원본과 결과물의 내용이 무엇이었는지를 기록합니다. 공개 내용을 갱신할 때 검토 기록도 갱신하고, 기존 릴리스의 기록은 태그 안에 보존합니다. dev의 새 변경을 비교하는 일과 발행한 릴리스가 그 기준에 맞는지 확인하는 일은 구분합니다.

`releases/latest`는 시간이 지나면 다른 릴리스를 가리킬 수 있습니다. 적용을 시작할 때 릴리스의 태그와 커밋을 확인하고, 그 기준의 `APPLICATION.md`에서 관련 문서를 이어 읽습니다. 작업 중 다른 기준을 섞지 않으며, 완료 시 실제 참고한 기준을 남깁니다. 사용자가 특정 태그·커밋·dev 작업 트리를 지정했다면 그 기준을 따릅니다.

## Mekra Method 릴리스

Mekra Method는 OKF Lab과 OKF Method의 지식과 이력을 이어받은 이름이다. 저장소는 `okf-lab`, `okf-lab-kr`, `okf-lab-dev`에서 `okf-method`, `okf-method-kr`, `okf-method-dev`를 거쳐 각각 `mekra-method`, `mekra-method-kr`, `mekra-method-dev`로 개명했다. 기존 `okf-0.2-lab-1` 태그와 그 커밋은 과거 기준점으로 보존하며, 과거 적용 기록의 저장소명과 태그를 새 이름으로 소급해서 바꾸지 않는다.

### 이름과 변경의 의미

새 릴리스 태그는 `mekra-X.Y`를 기본으로 하고, 패치를 별도로 배포할 때 `mekra-X.Y.Z`를 사용합니다. `X`, `Y`, `Z`는 숫자이며, 어떤 자리를 올릴지는 기존 적용과 운영에 주는 영향으로 판단합니다.

| 자리 | 변경의 의미 |
| --- | --- |
| 주 버전 `X` | 기존 적용의 중요한 전제나 운영 방식을 다시 검토해야 하는 변화 |
| 부 버전 `Y` | 기존 적용을 유지하면서 선택적으로 받아들일 수 있는 개선 |
| 패치 버전 `Z` | 의미를 바꾸지 않는 오류·표현·링크 수정 등을 별도로 배포하는 경우 |

`mekra-X.Y`는 해당 계열의 첫 릴리스이며 패치 0에 해당합니다. 같은 기준에 `.0` 태그를 중복 발행하지 않고, 후속 패치는 `.1`부터 올립니다. 부 버전을 올리면 패치는 다시 생략하고, 주 버전을 올리면 부 버전은 0부터 시작합니다. 예를 들어 `mekra-0.3`, `mekra-0.3.1`, `mekra-0.4`, `mekra-1.0`처럼 표기할 수 있습니다. 이는 이름의 예시이며 실제 발행이나 다음 번호의 지정을 뜻하지 않습니다.

이 구분은 방법론의 변경 영향을 설명하는 자체 규칙입니다. 소프트웨어 API의 호환성 보증으로 해석하지 않으며, 오류 수정이라도 적용 의미가 달라지면 그 영향에 맞는 자리를 올립니다. `MEKRA.md`의 시험 도입처럼 선택적 구성을 추가했다는 사실만으로 주 버전을 올리지는 않습니다. 의미를 유지하는 문서 개선은 공개 `main`에 수시로 반영할 수 있으며, 정식 적용 기준의 갱신은 릴리스로 발행합니다.

### OKF 기준과의 관계

Mekra 버전과 OKF 명세 버전은 독립적으로 기록합니다. 릴리스 이름에 OKF 버전을 결합하지 않고, 릴리스 설명에 기반·권장 OKF 버전과 검토한 명세 기준점을 명시합니다. 추가 지원 범위를 주장하려면 확인한 범위도 설명합니다. 대상 번들의 형식 선언은 계속 `okf_version`을 사용합니다.

OKF 기준을 바꿀 때는 실제 적용에 미치는 영향을 검토해 Mekra의 변경 수준을 판단합니다. 명세 번호가 달라졌다는 이유만으로 Mekra의 주 버전을 올리거나 번호를 다시 시작하지 않습니다.

### 기존 기준에서의 전환

2026-09-26 dev에서 이 규칙을 채택했습니다. 이전의 `okf-<명세 버전>-method-<순번>` 규칙과 `okf-…-lab-…` 계열로 발행한 태그는 그 이름과 대상을 보존합니다. 과거 순번을 새 버전 숫자로 기계적으로 변환하거나 기존 태그를 바꾸지 않습니다. 인박스에서 검토한 `mekra-0.x-okf-0.y` 결합 표기는 채택하지 않았습니다.

새 체계의 첫 번호는 실제 발행할 내용과 전환 영향을 검토해 정하고, 첫 릴리스 설명에 이전 공개 기준과 바뀐 내용을 연결합니다. 규칙의 채택만으로 릴리스가 발행되거나 대상의 적용 기준이 바뀌지는 않습니다.

### 언어별 발행

한국어판 `mekra-method-kr`과 영문판 `mekra-method`는 같은 논리적 릴리스 이름을 사용합니다. 같은 dev 기준에서 공개 범위와 의미를 검토한 두 판의 커밋에 각각 태그를 붙이므로 커밋 해시는 다릅니다. 태그는 발행한 커밋에 고정하고, 이후 수정은 후속 커밋에 남기며, 정식 적용 기준에 포함할 때 새 릴리스로 발행합니다. 릴리스 설명에는 주요 변화, 적용·전환 영향과 별도의 OKF 기준을 각 판의 언어로 기록합니다. 릴리스 본문에는 각 판의 해당 태그에 고정된 `README.md`와 `APPLICATION.md` 링크를 둡니다. 두 판의 확인이 끝난 뒤 같은 정식 릴리스를 최신으로 지정하고, 양쪽 `releases/latest`의 목적지도 확인해야 공통 릴리스가 완료됩니다. 이 관계의 판단 근거는 [배포 원칙](../okf/distribution.md)에 있습니다.

연구개발 저장소의 모든 커밋에 태그를 붙일 필요는 없습니다. 공개판의 `SYNC.json`이 검토한 dev 기준을 연결하며, 사용자 측의 회고에는 참고한 공개판만으로 당시 가이드를 확인할 수 있어야 합니다.

## 실제 참고 기준을 남길 때

최신 릴리스로 시작했다면 실제 확인한 릴리스 태그와 커밋을 기록합니다. `latest`라는 이동 가능한 URL만으로 당시 기준을 식별하지 않습니다. 공개 `main`이나 릴리스 후보·dev를 참고했다면 실제 커밋을 확인하고, 릴리스와 다른 내용을 가까운 태그의 내용으로 기록하지 않습니다. [적용 인계](../APPLICATION.md)에서 실제 읽은 저장소와 커밋을 기존 README나 운영 안내에 짧게 남기면 이후 비교에 도움이 됩니다. 해당하는 릴리스와 명세 기준도 구분해 적을 수 있지만, 별도 `VERSION` 파일이나 모든 개념의 메타데이터로 반복할 필요는 없습니다.

일부 개념만 새 가이드를 참고해 갱신했다면 그 범위를 함께 남겨, 저장소 전체가 같은 기준으로 전환됐다고 오해하지 않게 합니다. 과거 기준이 기록되지 않았다면 이력에서 확인할 수 있는 만큼 찾고 미확인 부분은 그대로 둡니다. [장기 피드백](../FEEDBACK.md)에서는 당시 기준과 현재 가이드의 차이를 관찰한 문제와 연결합니다.

`MEKRA.md` 같은 적용 안내에서 `version`을 사용한다면, 지식체계를 구성하거나 갱신할 때 참고한 Mekra Method 릴리스를 뜻합니다. 개별 지식의 개정 번호·최신성이나 전체 전환 완료를 뜻하지 않습니다. 실제로 참고한 릴리스 이름을 적고, 릴리스에 포함되지 않은 내용을 사용했다면 저장소·커밋과 적용 범위로 보완합니다. 별도 파일이나 필드의 사용은 필수가 아닙니다.

방법론 자체를 개발하는 dev에서는 채택된 지식이 있는 작업 트리를 적용 기준으로 설명할 수 있습니다. 미커밋 변경이 있으면 그 상태를 구분하며, 아직 발행하지 않은 번호를 적용 릴리스처럼 적지 않습니다. 비교·재현을 위해 상태를 고정할 때는 해당 커밋을 남깁니다.

## 초기 메타데이터 관례를 검토할 때

기존 자체 관례와 공식 필드의 의미가 다르면 실제 소비자가 어떻게 읽는지와 현재 적용 범위를 확인합니다. 아래 공식 의미는 [현재 기준점](current.md)과 같은 [OKF v0.2 명세 §5.2·§5.4](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/ad30107c31c06aec8a7d5636e0d1058118604e6f/SPEC.md#52-trust-generated-and-verified)에 근거하며, 전환 방법은 이 저장소의 적용 판단입니다.

| 기존 관례 | 공식 의미와 전환 판단 |
| --- | --- |
| `generated.at`을 최초 작성일로 유지 | 공식 의미는 마지막 의미 있는 내용 변경 시각입니다. 실제 작성·변경 근거가 있으면 맞추고, 미확인이면 시각을 만들어 넣지 않습니다. 선택 필드를 생략하거나 최초 작성 이력을 별도 기록에 보존할 수 있습니다. `generated`를 남길 때는 필수 하위 키인 `by`도 확인합니다. |
| 운영 중이라는 뜻의 `status: active` | 공식 문서 상태는 `draft`, `stable`, `deprecated`이며 생략 시 `stable`입니다. 운영 상태는 본문이나 확장 필드에 보존하고 문서 상태는 실제 의미에 맞게 판단합니다. `active`를 일괄적으로 `stable`로 바꾸지 않습니다. |
| 내용 변경 후 과거 `verified`를 현재 검증으로 해석 | 생성·변경과 검증은 별개입니다. 실제 재검증 없이 검증자나 시각을 갱신하지 않습니다. 과거 검증의 유효 범위를 살피고 현재 내용을 지지하지 못하는 표시는 정정하며, 필요한 과거 근거는 이력에 보존합니다. |

선택 필드를 늘리는 것 자체가 품질 개선은 아닙니다. 보호된 참조본이나 과거 사본의 의미를 보존하고, 이번에 적용할 범위에서 필요한 호환성만 검토합니다. 이런 보완만으로 명세 버전 승격이나 전면 재작성을 요구하지 않습니다.

## upstream 변경을 반영하는 흐름

1. 공식 `SPEC.md`의 버전과 diff를 확인합니다.
2. 형식 호환성, 의미 변화, 운영 원칙과 template에 미치는 영향을 나눠 평가합니다.
3. 필요한 문서만 갱신하고 기존 프로젝트의 migration 필요 여부를 기록합니다.
4. 새 프로젝트 권장 버전과 기존 프로젝트의 전환 우선순위를 별도로 판단합니다.

버전 번호만으로 호환성을 단정하지 않습니다. 같은 버전 표기 아래 명세가 바뀔 수 있으므로 확인일과 upstream 파일 기준점을 함께 남깁니다.

명세 기준점은 [현재 기준](current.md)에 SPEC blob과 그 내용이 일치하는 고정 커밋의 파일 링크로 남깁니다. 릴리스 설명에서도 검토한 고정 링크를 사용하면 당시 명세를 직접 확인할 수 있습니다. dev snapshot은 오프라인 검증·변경 비교에 보관본이 실제 필요할 때, Fork는 OKF 수정·배포나 별도 호환 분기의 유지가 필요할 때 검토합니다.
